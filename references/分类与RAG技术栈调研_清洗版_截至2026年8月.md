## A. 文本分类（提示词工程 / LLM 分类）

### A1. 分类提示词优化递进：零样本 → 少样本 → 思考链

| 阶段 | 做法 | 关键事实 | 来源 |
| :--- | :--- | :--- | :--- |
| 零样本（zero-shot） | 直接给分类指令 + 类别定义 | 最省 token、最易实现；对类别边界模糊的任务准确率低于少样本 | 🔶教材提炼；[VIPS Learn Few-Shot Prompting](https://learn.engineering.vips.edu/concepts/few-shot-prompting)（2026） |
| 少样本（few-shot） | 在 prompt 中给出若干「输入→正确类别」示例 | 显著提升；示例质量（代表性、覆盖类别分布）比数量更关键 | [Tetrate Few-Shot Learning Guide](https://tetrate.io/learn/ai/few-shot-learning-guide)（2026）；[IBM Research 开源 LLM 文本分类对比](https://research.ibm.com/publications/comparative-study-of-open-source-llms-for-text-classification-and-knowledge-extraction-in-the-material-discovery-domain)（2025） |
| 思考链（CoT） | 先让模型推理再给结论；或给出「思考→结论」示例 | 对复杂/多条件分类有效；对简单分类未必带来收益，且增加延迟与 token 成本 | 🔶教材提炼；[VIPS Learn](https://learn.engineering.vips.edu/concepts/few-shot-prompting)（2026） |

**few-shot 给几条最划算（收益是否递减、最优区间）**

- ✅官方研究证据：ICL（in-context learning）中「最优示范数量」是部署 ICL 的基础问题——[arXiv 2603.28043《Seeing the Unseen: Rethinking Illicit Promotion Detection with In-Context Learning》](https://arxiv.org/abs/2603.28043)（2026-03，⭐️需关注其最优 shots 的实验结论）。
- ⚠️待核验：另一 2026 年研究显示「shots 数量与模型效果呈**非线性关系**」——[Scientific Reports《Automated RECIST tumor response classification through prompt-guided LLMs》](https://link.springer.com/article/10.1038/s41598-026-54979-y)（2026）。即：存在收益递增段、平台期、以及（示例过多/过长时）收益回落段。
- 🔶教材提炼（业界通行经验，待核验到具体论文）：单条 prompt 内 **3–8 条示例为常见甜点区**；超过约 8 条后收益明显递减，示例总长挤占上下文、引入噪声时甚至变差。可复现实验参考：[a-dwivedi/few-shot-prompting-study（5 个 LLM × AG News 分类）](https://github.com/a-dwivedi/few-shot-prompting-study)。
- ⚠️待核验：输入长度对 ICL 效果存在独立影响——[EMNLP 2025《Input Length》](https://aclanthology.org/2025.emnlp-main.1514.pdf)（2025；⚠️信息较早：单条结论截止 2025-11，以原文为准，官方入口 https://aclanthology.org）。

> 结论要点（事实层面）：**「越多越好」不成立**；收益曲线非线性；示例质量（与目标分布的匹配度）与条数需分别对待。

### A2. 结构化输出：JSON mode / Structured Outputs / schema 校验

#### OpenAI（Structured Outputs）

| 项 | 事实 | 来源 |
| :--- | :--- | :--- |
| 能力 | 基于约束解码（constrained decoding）保证输出**严格符合** JSON Schema，语法级保证 | ✅官方：[OpenAI Structured Outputs Guide](https://platform.openai.com/docs/guides/structured-outputs)（自 2024-08 起持续演进，2025–2026 覆盖 GPT-4o/4.1/o 系列/GPT-5 系列） |
| 触发方式 | `response_format: {type: "json_schema", json_schema: {...}}` 或函数调用 `strict: true` | ✅官方同上；[OpenAI 开发者社区：Strict Output 文档与辅助代码](https://community.openai.com/t/tip-api-creation-of-structured-strict-output-documentation-improved-a-bit-with-helper-code/1356786)（2026） |
| 生态 | Zod / Pydantic 等 schema 库与官方 SDK 集成成熟 | [apidog 指南](https://apidog.com/blog/openai-structured-outputs/)（2026） |

#### DeepSeek（重点：是否只有 json_object、是否已支持 schema 强校验）

- ✅官方（截至 2026-08 快照）：DeepSeek API 官方文档仍以 **JSON Output（JSON mode）** 形式提供，即 `response_format: {"type": "json_object"}`；文档明确要求 **prompt 中必须出现「json」字样**，模型才会以 JSON 格式输出，返回体可直接 `json.loads`。官方文档**未提供 JSON Schema / schema 强校验接口**。——[DeepSeek API Docs: JSON Output（中文）](https://api-docs.deepseek.com/zh-cn/guides/json_mode/)、[（English）](https://api-docs.deepseek.com/guides/json_mode/)（截至 2026-08 官方页面）。
- ⚠️待核验：DeepSeek-V3.2（2025-10 发布）是否新增 structured output 属于高频社区提问——[Milvus Blog FAQ《Does DeepSeek-V3.2 support structured JSON mode?》](https://blog.milvus.io/ai-quick-reference/does-deepseekv32-support-structured-json-mode)（2025–2026）。结论倾向仍是「JSON mode，非 schema 强校验」，但**落地前必须复查官方文档最新状态**（本报告无法逐字确认该 FAQ 结论，标注待核验）。⚠️信息较早：V3.2 为 2025-10 版本，2026-08 最新模型线以官方 API 文档为准（核验入口：https://api-docs.deepseek.com）。
- ⚠️待核验：DeepSeek JSON mode 的已知注意点（如 temperature 建议、非法 JSON 概率、reasoner 模型的兼容性）随版本变化，见官方文档更新日志。

| 对比维度 | OpenAI Structured Outputs | DeepSeek JSON mode |
| :--- | :--- | :--- |
| 语法级保证 | ✅ 约束解码，schema 严格 | ❌ 无 schema；仅提示式 JSON 输出 + 概率性保证 |
| 接口形态 | `json_schema` / function `strict` | `json_object`（仅此一种 type） |
| schema 校验 | 服务端校验 + 客户端二次校验 | 需自建（如 Pydantic 解析失败重试） |
| 适合场景 | 需要强类型契约的生产链路 | 轻量分类、内部工具、低成本快速落地 |

### A3. 评估指标：准确率陷阱、P/R/F1、混淆矩阵、成本矩阵

| 指标/工具 | 关键事实 | 来源 |
| :--- | :--- | :--- |
| 准确率陷阱 | 类别不平衡时准确率失真（多数类主导）；LLM 分类器尤其需要按类别看 P/R | [FutureAGI《Evaluating LLM Classifiers in 2026》](https://futureagi.com/blog/evaluating-llm-classifiers-2026/)（2026）；[The Neural Base 准确率与分类](https://theneuralbase.com/llm-benchmarks/learn/beginner/accuracy-for-classification/) |
| 精确率/召回率/F1 | 单类视角；F1 是 P/R 调和平均 | [FutureAGI《F1 Score in 2026》](https://futureagi.com/blog/f1-score-evaluating-classifiers-2025/)（2026） |
| micro / macro / weighted | micro=按样本汇总计算（受多数类影响）；macro=各类别平均（对少数类敏感）；weighted=按类别样本数加权的 macro（**类不平衡时的常用默认**） | [FutureAGI《What Is the F1 Score?（micro vs macro vs weighted）》](https://futureagi.com/glossary/f1-score/)（2026） |
| 混淆矩阵 | 展示错分模式（哪两类最易混淆），LLM 分类部署前必看 | 🔶教材提炼（统计学习通用知识） |
| 成本矩阵（代价敏感） | 不同错误的代价不同（如漏判敏感件 ≫ 误判普通件）；优化目标应为「期望代价最小」而非单纯 F1 | 🔶教材提炼；与本书「敏感件零漏判」红线一致（教材口径） |

> 事实要点：2026 年针对 LLM 分类器的评估实践普遍强调**按类别分层评估 + 混淆矩阵 + 代价意识**，而非单一 accuracy；weighted-F1 是类不平衡场景的常见默认汇总指标。

### A4. 部署：置信度路由与批处理 vs 实时

#### 置信度路由（按 confidence 分流：自动 / 人工复核 / 人工）

- 2026 年研究：黑盒 LLM 的置信度构造方式（verbalized probability、logprob、meta-model 打分等）直接影响路由效果，存在「分数粒度缺口」——[arXiv 2606.22179《The Score Granularity Gap in Black-Box LLM Classification》](https://arxiv.org/html/2606.22179v2)（2026-06）。
- 混合人机审核中「何时升级到人」可用性能预测器学习——[Technion《LLM Performance Predictors: Learning When to Escalate in Hybrid Human-AI Moderation Systems》](https://cris.technion.ac.il/en/publications/llm-performance-predictors-learning-when-to-escalate-in-hybrid-hu/)（2025）；[ACL 2025 Findings《Evaluating LLMs for Confidence-based Check Set Selection》](https://aclanthology.org/2025.findings-acl.836/)（2025）。
- 工程样例：低置信度自动触发 human-in-the-loop 兜底——[RANJANA12-SHUKLA/Self-Healing-Classification-DAG](https://github.com/RANJANA12-SHUKLA/Self-Healing-Classification-DAG-with-Fine-Tuned-Model)（2026）；[AnthusAI/Classification-with-Confidence](https://github.com/AnthusAI/Classification-with-Confidence)（2025–2026）。
- 事实要点：置信度路由的成立前提是「置信度信号可靠」；2026 年文献指出 LLM 概率输出与真实正确率常不对齐，需校准或学习式评分。

#### 批处理 vs 实时调用

| 维度 | 批处理（Batch） | 实时（Online） |
| :--- | :--- | :--- |
| 适用 | 离线分类大量存量文本、可接受分钟级延迟 | 在线请求、交互式审核流 |
| 成本 | 明显更低（多家厂商批量 API 有折扣/半价类机制） | 单次计费，无批量折扣 |
| 注意 | 批量任务的结果回收与重跑机制 | 延迟预算与并发控制 |

- ⚠️待核验（定价具体数值）：OpenAI/Anthropic 等批量 API 折扣比例随模型与时间变化，落地前查官方定价页（核验入口：OpenAI 定价页 https://openai.com/api/pricing/ 与批量指南 https://platform.openai.com/docs/guides/batch；Anthropic 定价页 https://www.anthropic.com/pricing 与批量处理文档 https://docs.anthropic.com/en/docs/build-with-claude/batch-processing）；架构取舍参考 [Parasail《How to choose a managed inference architecture》](https://www.parasail.io/blog/how-to-choose-the-right-inference-architecture)（2026）；批量编排样例见 [Claude-Skills/batch-api-orchestrator](https://github.com/borghei/Claude-Skills/blob/main/engineering/batch-api-orchestrator/SKILL.md)（2026）。
- 🔶教材提炼：FDE 实务中「能批量就不实时」是成本控制常用原则；实时路径才需要考虑置信度路由与兜底队列。

### B2. 分块策略：chunk_size / overlap / 语义分块 / 父子文档 / 上下文检索

| 策略 | 解决什么问题 | 关键事实/推荐值 | 来源 |
| :--- | :--- | :--- | :--- |
| 固定长度分块（chunk_size + overlap） | 基线方案；把长文档切成可嵌入的片段 | 常见起点 **256–1024 tokens**（中文场景经验值 **512–1024** 常用）；overlap 常用 **10%–20%**；⚠️具体最优值因语料/检索器而异，属经验值 | 🔶教材提炼 + [面试鸭：chunk_size 与 overlap 怎么设](https://www.mianshiya.com/history/1985488284171722753/question/1991796741313175553)（2026）；[NVIDIA《Finding the Best Chunking Strategy for Accurate AI Responses》](https://developer.nvidia.cn/blog/finding-the-best-chunking-strategy-for-accurate-ai-responses/)（NVIDIA 开发者官方博客；⚠️信息较早，数值作通用经验参考，落地前核验最新） |
| 语义分块（semantic chunking） | 按语义边界（主题/段落）切分，减少「一句话被切断」 | 在特定评测中表现出色（如 2026 国际招生问答系统评测：Semantic Chunking + Dense Retriever 组合得分最高）⚠️信息较早（2025 论文，单条评测结论以原文为准） | [MDPI Electronics 14(15):3095](https://www.mdpi.com/2079-9292/14/15/3095)（2025）；[DLR《Impact of Chunking Strategies on Domain-Specific IR in RAG》](https://elib.dlr.de/221921/) |
| 父子文档（parent-child / ParentDocumentRetriever） | 小片嵌入提高召回精度，检索命中后回取父级大块供 LLM 读，兼顾「精检索 + 全上下文」 | LangChain 官方检索器实现 | ✅官方：[LangChain 官方仓库 parent_document_retriever.py](https://github.com/langchain-ai/langchain/blob/master/libs/langchain/langchain/retrievers/parent_document_retriever.py) |
| 上下文检索（Anthropic Contextual Retrieval） | 每个 chunk 嵌入前，先用 LLM 为 chunk 补写一段「它在文档中的位置/主题」上下文，解决 chunk 脱离文档语境导致召回失败 | Anthropic 官方博客（2024-09）：基准上检索失败率显著下降（上下文嵌入约 −49%，叠加 BM25 约 −67%，最终失败率约 1.9%）⚠️精确数字以原文为准；成本=每个 chunk 一次 LLM 调用（可用 Haiku 类小模型）；⚠️信息较早（2024-09 官方数据，截至 2025-11 之前；2026 年是否有更新方案以 Anthropic 官方 engineering 博客为准，核验入口：https://www.anthropic.com/engineering） | ✅官方：[Anthropic《Contextual Retrieval》](https://www.anthropic.com/engineering/contextual-retrieval)（2024-09） |

> 事实要点：分块没有万能最优值；2026 年主流实践从「纯固定长度」转向「固定长度做基线 + 语义/父子/上下文检索按需增强」；中文场景注意按中文标点与语义边界切分（🔶教材提炼）。

### B4. 向量数据库选型：Chroma / Milvus / pgvector

| 维度 | Chroma | Milvus | pgvector |
| :--- | :--- | :--- | :--- |
| 定位 | 嵌入式（embedded）向量库，Python 原生，本地文件持久化 | 分布式、云原生独立向量数据库 | PostgreSQL 扩展 |
| 部署 | 进程内库/轻量 server，开箱即用 | 单机 docker 或集群（K8s）；有托管（Zilliz Cloud） | 随 Postgres 部署（含云 RDS） |
| 索引 | HNSW（默认）等 | HNSW、IVF、DiskANN、GPU 索引等，支持稀疏/稠密/混合 | HNSW（pgvector 0.5+）、IVFFlat；无专用稀疏索引（可用 tsvector/全文） |
| 混合搜索 | 基本（dense 为主） | 原生支持 dense + sparse + 混合检索（2025–2026 主打能力） | dense 向量 + SQL/tsvector 全文可拼混合（自建融合） |
| 适用规模 | PoC / 小规模（万级–百万级内） | 生产、大规模（亿级向量基准常见对象） | 百万级内、数据本就在 Postgres 时 |
| PoC vs 生产 | PoC 首选之一；生产需要评估其多机扩展性 | 生产首选之一 | 中小规模生产、不想引入新组件时 |

**来源（均为第三方对比/基准，标注待核验）：**

- ✅官方/仓库：100M 向量综合基准（pgvector/Pinecone/Weaviate/Chroma/Qdrant/Milvus 的 recall@k、QPS、延迟、成本）——[jhondados/vector-database-benchmark](https://github.com/jhondados/vector-database-benchmark)（2025–2026 持续更新）
- [腾讯云开发者：向量数据库选型：从 Chroma 到 Milvus，企业场景怎么选](https://cloud.tencent.cn/developer/article/2664756)（2026）
- [Waterflai：Milvus vs ChromaDB](https://www.waterflai.ai/blog/milvus-vs-chromadb-choosing-the-right-vector-database-for-your-ai-applications/)（2026）
- [Redis Blog：Best open source vector databases (2026)](https://redis.io/blog/best-open-source-vector-databases-comparison/)（2026，⚠️RediSearch 赞助内容）
- [arXiv 2608.12812：向量数据库 ANN 系统实证评估](https://arxiv.org/abs/2608.12812)（2026-08）
- [cnblogs：千万级向量数据库大比拼](https://www.cnblogs.com/Im-Victor/p/19099016)（2026）

> 事实要点：PoC 阶段 Chroma 上手成本最低；生产大规模、需要稠密+稀疏混合检索时 Milvus 是主流选项之一；数据已在 Postgres、规模百万级内时 pgvector 免去新组件。三者具体性能需按自己的数据跑基准（[vector-database-benchmark](https://github.com/jhondados/vector-database-benchmark) 可复现）。

### B5. 检索增强递进：基础 → 混合 → 重排 → HyDE / 查询改写

| 阶段 | 解决什么问题 | 何时值得上 | 关键事实 | 来源 |
| :--- | :--- | :--- | :--- | :--- |
| 基础（纯 dense 向量召回） | 语义相似检索 | 语料规整、查询与文档用词接近 | 基线方案 | 🔶教材提炼 |
| 混合检索（dense + sparse/BM25） | 精确词匹配（编号、专有名词）与语义匹配互补；dense 漏掉的精确匹配由 BM25 兜住 | 语料含代码、编号、产品名、中文专名时显著提升 | 融合常用 RRF；中文场景常配 jieba 分词 BM25（FTS5+jieba 中文 RAG 工具链示例：[yiongq/mcp-chinese-rag-toolkit](https://github.com/yiongq/mcp-chinese-rag-toolkit)（2026）） | [raghub ADVANCED_RAG](https://github.com/sachncs/raghub/blob/master/docs/ADVANCED_RAG.md)（2026）；[RAGArena](https://github.com/tino-TL/RAGArena)（2026） |
| 重排（rerank，bge-reranker 等 cross-encoder） | 召回 Top-K 后精排：用 query×doc 深度交互模型重打分，修正向量相似度的粗召回 | 已做混合召回、对首屏精度敏感时；成本=对 Top-K 逐对推理，延迟/成本可控 | 第三方评测称 rerank 可带来显著精度提升（如 +40% 量级，⚠️依赖语料；⚠️信息较早：2025 年第三方数据，落地前核验最新或自测）——[ailog《Reranking for RAG: +40% Accuracy with Cross-Encoders (2025 Guide)》](https://app.ailog.fr/en/blog/guides/reranking)（2025）；中文主力：BAAI **bge-reranker-v2-m3**（cross-encoder，多语言含中文）——✅官方模型卡：[HuggingFace BAAI/bge-reranker-v2-m3](https://huggingface.co/BAAI/bge-reranker-v2-m3)（原 CSDN 技术解析已删，改为官方来源）；Qwen3-Reranker 亦可用（✅官方博客） | ⚠️第三方（2025，信息较早）+ ✅官方（BAAI 官方模型卡） |
| HyDE（Hypothetical Document Embeddings） | 查询过短/表达差异大时：先让 LLM 生成一段「假设答案文档」，再对它做 embedding 检索 | 查询是问句/口语化、与文档措辞差异大时 | 原论文：[arXiv 2212.10496《Precise Zero-Shot Dense Retrieval without Relevance Labels》](https://arxiv.org/abs/2212.10496)（2022，✅原文） | ✅原文 |
| 查询改写（query rewriting / multi-query / 分解） | 一次检索不够时：改写、多角度扩展、或拆成多个子查询分别检索再融合 | 复杂问题、多条件问题、检索为空时 | 工具链与工程讨论见 [raghub](https://github.com/sachncs/raghub/blob/master/docs/ADVANCED_RAG.md)、[langbot 插件 Issue](https://github.com/langbot-app/langbot-plugin-demo/issues/14)（2026） | ⚠️待核验 |

> 事实要点（递进逻辑）：**混合检索解决「召回漏」→ 重排解决「排序差」→ HyDE/查询改写解决「查询表达与文档不对齐」**；每一步都有明确触发条件与成本，不是默认全上（🔶教材提炼 + 上表证据）。

### B6. RAG 评估：RAGAS 三指标与当前版本

| 指标 | 中文含义（教材口径） | 衡量什么 |
| :--- | :--- | :--- |
| **Faithfulness（忠实度）** | 答案中的每个论断是否都能由检索到的上下文支撑 | 防幻觉：答案 vs 上下文 |
| **Context Precision（上下文精确度）** | 检索到的上下文中，相关片段是否排在前面 | 检索排序质量 |
| **Answer Relevancy（答案相关性）** | 答案与问题的相关程度（是否答非所问） | 答案 vs 问题 |

**版本与事实：**

- ✅官方：RAGAS 官方文档当前线为 **v0.4.x**（存在 v0.3 → v0.4 迁移指南，官方文档站点为 v0.4.2）——[docs.ragas.io v0.4.2 迁移指南](https://docs.ragas.io/en/v0.4.2/howtos/migrations/migrate_from_v03_to_v04/)（2025–2026）；指标全集含 Faithfulness、Answer Relevancy、Context Precision、Context Recall 等（[论文/系统综述列举](https://pmc.ncbi.nlm.nih.gov/articles/PMC11150590/)）。
- ⚠️待核验：最新小版本号（v0.4.2 之后）以官方 [PyPI ragas](https://pypi.org/project/ragas/) 与 [官方文档](https://docs.ragas.io) 为准；[日本技术博客 2026 版 RAGAS 介绍](https://www.issoh.co.jp/tech/details/16042/)提到 0.4 系实现路径（2026）。
- ⚠️待核验：v0.4 中 LLM 类指标的默认实现方式有变化（异步/底层 LLM 调用），中文语料评估需配置支持中文的 judge LLM；实操细节以官方文档为准。
