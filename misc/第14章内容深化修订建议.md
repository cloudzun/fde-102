## 三、章节显得单薄的主要原因

### 1. 多数小节只有结论与检查项，缺少机制解释

以超时、重试、熔断与降级为例，当前只给出了：

```text
短暂故障 → 有限次数重试
连续故障 → 熔断或暂停调用
不可恢复故障 → 安全降级或转人工
```

这个结论正确，但学员仍无法回答：

- 哪些错误适合重试；
- 哪些错误不应重试；
- 429、500、鉴权失败和超时应如何分别处理；
- 为什么要使用退避与随机抖动；
- 熔断器有哪些状态；
- 熔断后怎样探测恢复；
- 分类、RAG、路由工作流应如何分别降级；
- 重试是否会造成重复创建工单；
- 有副作用的动作怎样保证幂等。

配置、日志、权限、监控、灰度与回滚等小节也存在类似问题。

### 2. 缺少一张完整的目标生产架构图

当前章节从 Build Readiness Gate 直接进入多个生产主题，但没有先让读者看到分类 Demo 生产化后的整体系统结构。

建议增加一张端到端架构图，至少包括：

```text
业务用户
→ 接入层
→ 身份认证与权限
→ 业务服务
→ 模型或工具 Provider
→ 安全降级与人工队列

外围能力：
配置与 Secret
日志与链路追踪
指标与告警
审计存储
版本与发布控制
```

这张图用于解释各小节之间的关系，避免配置、日志、权限和告警变成互不关联的知识点。

### 3. 缺少贯穿全章的“改造前—改造后”案例

当前各节虽然有必做实验，但没有形成一条连续施工线。

建议以第 8 章分类器作为贯穿案例。

#### 改造前

- 使用 Streamlit；
- 一次请求调用一次模型；
- 小样本演示级验收；
- 外部服务失败时直接报错；
- 没有用户身份；
- 没有结构化运行指标；
- 没有灰度和回滚；
- 只有原作者知道如何运行。

#### 连续改造过程

```text
原型基线
→ 配置和 Secret 分离
→ 结构化日志与版本标识
→ 超时、有限重试和安全降级
→ 权限控制与审计
→ 指标、Trace 与告警
→ v1/v2 灰度与回滚
→ 运行手册与跨组接管
→ 工程能力跨 Demo 复用
```

#### 改造后

- 出错能够定位；
- 外部服务异常不会拖垮系统；
- 越权操作会被拒绝并留痕；
- 每次判断可以追溯到模型、Prompt、配置和数据版本；
- 新版本可以小范围验证；
- 退化后可以恢复已知稳定版本；
- 接管组能够独立运行。

### 4. 性能与容量进入 Gate，却没有对应正文

当前 `14.2` 将性能与容量列为生产准备维度，但后文没有专节讲解。这是明显的结构断点。

建议补充：

- P50、P95、P99 延迟；
- 吞吐量和并发数；
- 错误率和超时率；
- 队列等待时间；
- 模型服务限流；
- token 长度对延迟和成本的影响；
- embedding 批量大小；
- 人工审核队列容量；
- 单次调用成本和日/月预算；
- 峰值容量与安全余量。

需要让学员理解：

```text
平均流量能跑
≠
峰值流量能接住

模型服务能响应
≠
人工审核队列不会积压
```

### 5. 日志、审计和指标缺少 Trace、SLI 与 SLO

当前章节只区分日志、审计和指标，还不足以支撑高级工程判断。

建议补充：

#### Trace

一次 AI 请求可能经历：

```text
用户输入
→ 分类或检索
→ 模型调用
→ 工具调用
→ 人工审核
→ 最终动作
```

需要用 `trace_id`、`span_id`、步骤耗时和调用结果还原完整链路。

#### SLI、SLO 与 SLA

| 概念 | 含义 | 示例 |
|---|---|---|
| SLI | 实际测量的服务指标 | 最近 7 天请求成功率 |
| SLO | 团队内部期望达到的目标 | 成功率不低于 99.5% |
| SLA | 对客户作出的服务承诺 | 是否写入合同需另行确认 |
| Error Budget | 可容忍失败预算 | 在目标窗口内允许的失败量 |

需要强调：SLO 是工程治理工具，不应把演示环境中的短时数据直接写成客户 SLA。

### 6. 权限与安全目前主要停留在角色矩阵

RBAC 只是 AI 应用安全的一部分。建议建立五层安全框架：

1. **身份与权限**：谁能访问、配置和审批；
2. **数据安全**：分类分级、脱敏、日志保留和出域控制；
3. **模型安全**：输入校验、Prompt Injection、输出检查；
4. **工具安全**：白名单、参数校验、最小权限、高风险动作确认；
5. **供应链安全**：依赖、镜像、模型权重来源、哈希和漏洞。

不必把本章写成完整安全教材，但应让学员知道“模型有工具调用能力”不等于“模型有权执行所有动作”。

### 7. 工程 Scale 不能只等同于运行手册与接管

跨组接管很重要，但工程 Scale 还涉及：

- 单实例到多实例；
- 同步请求到队列处理；
- 高峰限流；
- 多部门、多租户和配置隔离；
- 数据增长与索引增长；
- 人工审核队列容量；
- 成本随业务量变化；
- 故障域；
- 备份与恢复；
- RTO 与 RPO；
- 值班、变更和发布责任。

这些内容不必全部要求学员实现，但必须建立判断框架，否则本章只能覆盖 Build 与交接，尚不足以覆盖 Scale。

### 8. 本体工程验证的知识前置不足

当前第 14 章要求验证本体的数据映射、动作接口和权限，但业务本体的完整知识计划放在第 15 章展开，容易造成先验证、后学习。

建议二选一：

1. 在第 3 或第 6 章提前埋下对象、关系、状态和动作的最小概念；
2. 在第 14 章本体工程验证前增加一张“本章只需知道什么”的知识卡。

并明确：

- 第 14 章不判断业务抽象是否正确；
- 第 14 章只验证已有对象、关系和动作能否映射到数据、接口、权限和状态；
- 第 15 章负责完整业务语义抽象和回注价值判断。

### 9. 范围过宽导致每项只能浅做

当前 10 项学习目标要求在约 5—6 小时内真实完成配置、日志、审计、指标、超时、重试、熔断、降级、权限、灰度、回滚、告警、事故响应、接管、复用和本体验证，实际难度过高。

建议采用“核心必做 + 进阶选做”分层，避免全员每项都只做表面动作。

# 第二层　讲透四项生产核心能力

## 14.4 可配置、可追溯

整合以下内容：

- 配置与 Secret；
- 环境分离；
- 代码、模型、Prompt、配置、数据和索引版本；
- 结构化审计链。

核心问题：

> 一次线上结果，能否还原到当时使用的完整版本与决策上下文？

应讲清：

- 配置来源与优先级；
- Secret 轮换；
- Prompt 版本标识；
- 模型/provider 切换；
- 数据和索引版本绑定；
- 审计不可篡改的基本思路；
- 日志脱敏。

## 14.5 可失败、可恢复

整合以下内容：

- 超时；
- 有限重试；
- 退避与随机抖动；
- 熔断；
- 降级；
- 幂等；
- 补偿；
- 人工兜底。

核心问题：

> 依赖失败时，系统能否进入一个可预测、可解释、可恢复的状态？

建议增加错误分类表：

| 故障 | 是否重试 | 处理建议 |
|---|---|---|
| 网络瞬时超时 | 可以有限重试 | 退避后重试，受总超时限制 |
| 429 限流 | 可以延迟重试 | 尊重服务端等待提示并限流 |
| 500 服务异常 | 视场景有限重试 | 超过阈值后熔断和降级 |
| 401/403 | 不应自动重试 | 检查配置与权限，避免放大错误 |
| 请求参数错误 | 不应重试 | 立即失败并修正输入 |
| 返回结构非法 | 可有限重试一次 | 仍失败则安全降级 |

有副作用的动作必须补充幂等和补偿说明。

## 14.6 可观察、可判断

整合：

- 日志；
- Trace；
- 指标；
- SLI / SLO；
- 告警；
- 成本；
- 数据和模型漂移。

核心问题：

> 怎样判断系统处于健康、退化还是失控状态？

建议按照四类指标组织：

| 指标类型 | 示例 |
|---|---|
| 系统指标 | 延迟、错误率、吞吐、资源占用 |
| 模型指标 | 解析失败、拒答、转人工、质量抽检 |
| 业务指标 | 类别分布、处理时长、返工率 |
| 成本指标 | token、单请求成本、日/月预算 |

## 14.7 可发布、可回退

整合：

- 六类版本；
- 灰度；
- 兼容性；
- 数据和索引迁移；
- 回滚；
- 发布决策。

核心问题：

> 新版本如何安全进入生产，出现退化后如何回到已知稳定状态？

需要特别提醒：

- 只回滚代码、不回滚 Prompt，结果可能仍然异常；
- RAG 只回滚代码、不回滚索引，结果可能仍然异常；
- 配置或数据结构不兼容时，简单切换版本可能无法恢复。

# 第三层　讲清工程 Scale

## 14.8 性能、容量与成本

这是当前版本必须补充的独立内容。

建议包括：

### 工作负载画像

- 平均请求量；
- 峰值请求量；
- 请求长度；
- 业务高峰时间；
- 同步或异步；
- 人工审核比例。

### 关键指标

- P50、P95、P99 延迟；
- 吞吐量；
- 并发数；
- 超时率；
- 队列等待时间；
- 单请求成本；
- 人工审核队列长度。

### 容量判断

```text
峰值业务量
× 单请求资源消耗
× 峰值与故障安全余量
→ 服务容量与人工容量
```

### 实验建议

对分类器进行小规模压测，观察：

- 并发增加时延迟怎样变化；
- provider 限流如何表现；
- 人工兜底比例上升时队列是否积压；
- 降级策略是否能够保护系统。

所有结论注明“仅本次环境与样本”。

## 14.9 权限、安全与治理

将现有 RBAC 扩展为五层框架：

```text
身份与权限
+ 数据安全
+ 模型安全
+ 工具安全
+ 供应链安全
```

正文重点讲最小权限、输入不可信、工具白名单、高风险动作确认、日志脱敏和依赖来源；更深入内容可作为进阶选读。

## 14.10 运行责任、客户接管与 FDE 撤出

保留跨组接管，并补充：

- RACI；
- 值班与升级路径；
- 配置和版本变更审批；
- 事故响应责任；
- 用户培训；
- 支持边界；
- RTO / RPO 基本概念；
- FDE 撤出条件；
- 撤出后的反馈和能力回注机制。

## 14.11 本体的工程实现与工程能力回注

将当前 `14.10` 调整到此处，并明确两部分：

### 业务本体工程验证

- 对象属性有稳定数据来源；
- 对象有身份和主键；
- 关系有维护机制；
- 状态变化有合法路径；
- 动作有真实接口或人工流程；
- 权限、审计、幂等和回滚可验证；
- 版本变化不破坏已有应用。

### 工程能力回注

- 配置加载；
- provider 适配；
- 日志和审计；
- 重试与熔断；
- 健康检查；
- 发布回滚；
- 告警规则；
- 运行手册模板。

至少选择一个机制在第二个 Demo 上完成冒烟复用，才能称为工程回注。

# 第四层　设计一条贯穿式生产化实验

## 14.12 从分类 Demo 到可运营服务

不建议继续把“实验（必做）”零散放在每节末尾。应把它们组织成一项连续实验。

### 阶段一：建立原型基线

1. 运行第 8 章分类器；
2. 记录当前代码、模型、Prompt 和数据版本；
3. 跑固定基线样本；
4. 记录功能、延迟、错误和转人工情况；
5. 填写 Build Readiness 初始状态。

### 阶段二：增加生产护栏

完成：

- 配置和 Secret 分离；
- 结构化日志；
- 超时和有限重试；
- 异常安全降级；
- 简单权限控制；
- 审计记录。

### 阶段三：增加运行证据

完成：

- 指标采集；
- Trace；
- SLI / SLO；
- 告警规则；
- 版本标识；
- 成本统计。

### 阶段四：发布和恢复

1. 保存稳定版 v1；
2. 修改 Prompt 或阈值得到 v2；
3. 小流量灰度；
4. 比较质量、延迟和成本；
5. 人为制造 v2 退化；
6. 触发告警；
7. 执行回滚；
8. 验证 v1 恢复。

### 阶段五：交接

1. 编写运行手册；
2. 接管组在不能询问原作者的情况下启动系统；
3. 接管组定位一个预设故障；
4. 接管组完成回滚和恢复；
5. 记录手册缺口并修订。

### 阶段六：工程回注

1. 选择一个通用工程机制；
2. 接入 RAG 或路由工作流；
3. 完成最小冒烟测试；
4. 记录需要修改的配置和代码；
5. 判断它是客户定制、回注候选，还是已验证的复用能力。

完整实验应让学员感受到：

```text
一个 Demo
如何一步步成长为
可配置、可追溯、可恢复、可发布、可观察、可交接的系统
```

## 五、建议采用“核心必做 + 进阶选做”

### 核心必做

所有学员完成：

1. 配置与 Secret；
2. 结构化日志与版本标识；
3. 超时、有限重试和安全降级；
4. 基础指标与告警；
5. v1 / v2 灰度与回滚；
6. 运行手册；
7. 跨组接管。

### 进阶选做

技术基础较好的学员完成：

- 完整熔断器状态；
- 分布式 Trace；
- SLO 与 Error Budget；
- RBAC；
- 幂等和补偿；
- 容量压测；
- 漂移检测；
- 可执行本体映射；
- 跨 Demo 工程组件复用。

这样既保证所有人真正做过生产化关键动作，又避免一个教学日把所有内容都浅尝辄止。

## 六、建议增加的案例与反模式

### 案例一：无限重试导致故障放大

```text
模型服务变慢
→ 应用不断重试
→ 请求进一步放大
→ 模型服务更慢
→ 请求全面堆积
```

教学点：重试必须有次数上限、退避、随机抖动和总超时。

### 案例二：Prompt 更新无法追责

用户投诉同一问题前后结果不同，但系统只记录模型名，没有记录 Prompt 和配置版本。

教学点：AI 系统的可追溯版本不只是代码版本。

### 案例三：RAG 回滚只回代码

代码回到 v1，但系统仍使用 v2 索引，结果继续异常。

教学点：回滚必须考虑代码、模型、Prompt、配置、数据和索引的联动。

### 案例四：接管组无法启动

原作者认为 README 已经完整，但接管组不知道：

- `.env` 从哪里获取；
- 数据怎样初始化；
- 健康检查是什么；
- 回滚入口在哪里。

教学点：文档是否有效，由接管者而不是作者判断。

### 案例五：告警触发但无人负责

错误率告警已经触发，但团队没有定义接收人、响应时限和处置动作。

教学点：没有责任人的告警不构成有效运营机制。

### 案例六：重复执行造成副作用

工单分派接口超时，系统不知道第一次调用是否成功，重试后把同一工单分派了两次。

教学点：涉及外部动作时必须设计幂等键、状态确认或补偿机制。

## 七、每个核心小节应采用的写作模板

为了把当前“检查清单”扩展成教科书正文，建议每个核心节统一包含：

1. **业务场景**：为什么会遇到这个问题；
2. **概念解释**：关键术语是什么；
3. **机制原理**：为什么这样设计；
4. **方案比较**：有哪些选择和权衡；
5. **西岭示例**：分类器中如何落地；
6. **反模式**：常见错误和后果；
7. **动手任务**：学员具体做什么；
8. **验收证据**：怎样证明做对；
9. **迁移问题**：换成 RAG 或路由工作流会有什么变化。

当前章节多数小节主要覆盖“概念结论、动手要求和验收提醒”。下一轮需要补足场景、原理、权衡、案例和迁移。
