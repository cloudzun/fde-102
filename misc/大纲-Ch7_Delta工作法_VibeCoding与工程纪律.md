### 7.1 为什么 FDE 需要 AI：主动拥抱、更要会驾驭（本节为全章论证根基）
> **本节定位（主编要求）：** 不先讲"AI 工具操作"，先把**"FDE 为什么需要 AI、Delta 如何用 AI 挖掘潜力、加速 FDE 项目高质量完成"**讲透——这是全章的根基；并立一个时代视角：**AI 技术要主动积极采用、极大赋能，但 AI 本身又需要驾驭，因此 Delta（以及 Echo）必须具备"获得 AI 赋能 + 良好驾驭 AI"两方面的视野与能力。**后面 7.2 选层、7.3 选模型、7.4 部署、7.5 工具、7.6 流程、7.7 纪律，全部挂靠在本节建立的逻辑上。
> **方法论来源（不复制原文）：** 本节观念对齐在线全书 https://www.cloudzun.com/fde-course/（AI FDE 落地·共识与对齐）的"两种偏差 + 重新定义产能瓶颈"论断，以及本书第 3 章 3.2 / 第 4 章 4.5 的"人能判断、AI 能执行"分工哲学。

- 7.1.1 先把 FDE 放在 PPT 与四阶段里看（承接 3.1/3.3）：
  - PPT（People–Process–Technology）：People 是根、Process 是脉、**Technology 是器**——本章讲的"用 AI 干活"正是 Technology("器")这一维在当前时代的重写。
  - 四阶段（Discovery→Prototype→Build→Scale）：Delta 主导 **Prototype（双角色）/ Build（主导）/ Scale（自运营+回注）**——"用手把施工图做出来"主要落在 Prototype/Build 两段；AI 赋能 Delta，正是赋能这两段的产能。
  > 图：图 7-1 FDE 交付三维（PPT）+ 四阶段中 Delta 的主导段（垂直 TB，>4 节点，可并入一张）。

- 7.1.2 Delta 的价值从哪来：**交付速度 × 交付质量 × 可复用性（能力回注）**。承接 3.2.2 / 4.4：Delta 靠做、70/20/10（编码/联调/回注）、回注不可省（卖人力→卖能力）。

- 7.1.3 FDE 项目的高质量卡在哪——**用 PPT 看 Technology（器）的三个产能瓶颈**（这是"为什么需要 AI"的根源，也是"AI 与己无关"偏差的破法）：
  - **时间瓶颈**：客户现场时间有限，Prototype/Build 两段要在几周内从零做出"可演示 + 可上生产的最小系统"，传统手写来不及；
  - **广度瓶颈**：一个 Delta 要覆盖数据管道、后端、前端、AI 集成、部署，人力不可能全栈精通；
  - **复用瓶颈**：能力回注四步法（识别→抽象→集成→验证）要求把"本次经验"变成"下次可复用资产"——纯手工做，识别与抽象成本极高，容易退化回"卖人力"。
  > 表格：表 7-1 三个瓶颈（挂 PPT Technology/四阶段 Prototype-Build）× 现象 × 若不解决会怎样。

- 7.1.4 立两个方向，避免两种偏差（对齐 AI FDE 落地·共识与对齐 15.1）：
  - **偏差一"AI 万能论"**：以为有 AI 就不需要懂业务的工程师在现场——错。AI 解决"写得快"，不解决"知道该写什么、写出来有没有人用"。
  - **偏差二"AI 与己无关"**：以为 FDE 的活（数据管道、异构集成、现场推动）AI 碰不到——错。AI 正在系统性地吃掉 FDE 工作里**最可标准化、最重复**的部分。
  - **结论**：AI 放大 FDE 的"复合能力"——让懂业务的人写代码更快，让写代码的人更快理解业务；**不改变定位，但重新定义产能瓶颈**。→ 主旋律就是"**主动采用 AI，同时驾驭 AI**"。

- 7.1.5 角色演变（承接"人能判断、AI 能执行"，不新造框架）：
  - FDE 从"写每一行代码"转向"**写关键的代码 + 编排 AI 干重复的活 + 把关 AI 的产出**"（AI FDE 落地·共识与对齐的 Delta 视角表述；落地本书 4.5）。
  - **判断（人）** 与 **执行（AI + 人在 checkpoint 把关）** 两条能力缺一不可；AI 承担重复、可标准化部分，人负责"什么是对、哪里会出事、什么时候拍板"。
  - **对 Delta（本章主体）**：需要"获得 AI 赋能"（会用 code agent 交付）+ "驾驭 AI"（懂选型、能防翻车、守质量闭环）两方面的视野与能力。
  - **对 Echo（点到，承接第 15/5 章）**：获得 AI 赋能 + 驾驭 AI 同样重要——用 AI 做访谈分析、痛点聚类、方案速读，同时审 AI 洞察是否是真痛点、不被"看似合理"带偏；Echo 侧重"判断"，但也要会用 AI 工具提效。
  > 表格：表 7-2 人/AI 在 FDE 交付中的职责分工（判断 vs 执行）+ Delta/Echo 各自的 AI 视野要点。
  > 反模式预告：把"用 AI"当"让 AI 全自动"（见 7.7 纪律三 / 反模式节）；把 AI 当万能或与己无关（7.1.4）。

### 7.4 本地部署底座与"数据不出域"（新增·红线落地;挂靠 7.1"判断/部署约束" + 红线）
- 7.4.0 节首一句话：承接 7.1"判断"的部署约束，当"数据敏感度"判出"不能上云"，"跑在哪"就必须落到本地——这是"数据不出域"红线在技术侧的落地（对齐在线全书 AI FDE 落地 16.4.5）。
- 7.4.1 为什么需要本地：数据不出域是合规红线（政务/金融/国企）；PIPL + 数据跨境规定一句话背景。
- 7.4.2 引擎选型：Ollama（开箱即用/GGUF）/ vLLM（生产高吞吐）/ llama.cpp（底层）；开发用 Ollama、生产用 vLLM。
- 7.4.3 量化与硬件：FP16→Q4_K_M≈0.30×（30B MoE 可跑 24GB 卡）；GPU 行情一句话。
- 7.4.4 成本经济性：本地 vs API 盈亏平衡（约 1 万次/日）；"信息截至 2026-08"。
- 7.4.5 私有化交付：联网构建 → 打包 → 内网部署（信创可选：昇腾/CANN）。

### 7.6 gstack 工作流与 SPEC 驱动开发（把 v0.2 的 7.3+7.4 升格;把 7.1 的四步骨架组织成流水线）
- 7.6.0 节首一句话：7.1 的"描述意图→AI 执行→判断把关→质量闭环"四步，在本节落成一套可执行的流水线（gstack），并用 SPEC 把"意图"写死。
- 7.6.1 gstack 本质：Garry Tan/YC 开源，官方"23 个 opinionated tools"、核心闭环 plan→review→ship；**八/七环节为教材归纳**。
- 7.6.2 八环节流水线：office-hours → spec → autoplan → build → review → qa → ship → retro（每环人的职责；可能回溯）。
- 7.6.3 SPEC 驱动：先写规格（边界 No-Go / 数据模型 / 验收口径），build 只执行。
- 7.6.4 环节产出都是文件（可追溯、可复用 → 3 实操逐轮复用 AGENTS.md/retro.md）。

### 7.7 防 Agent 翻车的三条工程纪律（保留·本书精华;守住 7.1"判断"+质量闭环）
- 7.7.0 节首一句话：7.1 说"人负责判定、AI 负责执行"，但 AI 执行会"翻车"。三条纪律保证"驾驭 AI"落到实处——质量闭环不被 AI 的"自洽"击穿。
- 纪律一：测试数据必须外部给定（防 Agent 自证/自己出题自己考）。
- 纪律二：启动提示词写清 7 项信息块（背景/要做什么/输入输出/技术选型/数据现状+测试集/验收口径/约束）。
- 纪律三：驱动指令把流程纪律"焊"进 Agent（一环一停、拍板列选项、禁止全自动一把梭）。

## 反模式与红线
- 让 Agent 全自动一把梭、不设 checkpoint（失去中途纠偏）。
- Agent 自己出题自己考（测试数据不自造）。
- 把决策权丢给 AI；跳过 SPEC 直接 build。
- 把 .env/API key 入库。
- 忽略"数据不出域"硬上公网 API（红线）。
- 过度堆技术层（能提示词却上 Agent）——违背"从最简单开始"。
