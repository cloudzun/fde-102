# 第 14 章 FDE 化重构建议

> **文档用途：** 供教科书编写团队重构《第 14 章 Delta 工作法：Build、Scale 与工程化交付》  
> **评审对象：** `textbook/第14章_Delta工作法_Build_Scale与工程化交付.md`  
> **依据版本：** 教科书 v0.7 当前稿  
> **修订性质：** 章节定位与内容结构调整建议，不直接修改教科书正文  
> **核心结论：** 当前第 14 章写入了较多通用 DevOps、SRE 和服务运维内容，削弱了 FDE 特色。下一轮不应继续扩充通用运维知识，而应围绕“客户现场最后一公里”重构：验证原型假设、接入真实环境、闭合业务动作、完成客户接管，并把现场经验回注平台。

## 一、问题判断

当前第 14 章包含：

- 配置与密钥管理；
- 日志、审计与指标；
- 超时、重试、熔断与降级；
- 权限与最小权限；
- 版本、灰度与回滚；
- 监控告警与事故响应；
- 运行手册与跨组接管；
- 工程能力回注；
- 业务本体工程验证。

这些内容本身都正确，也确实是生产系统需要考虑的工程要素。但如果逐项展开，本章容易变成一章通用的 DevOps / SRE / 平台工程入门课。

FDE 教科书不需要完整教授：

- 如何实现熔断器；
- 如何搭建监控平台；
- 如何部署分布式链路追踪；
- 如何建设高可用集群；
- 如何编写完整 RBAC 框架；
- 如何配置 Kubernetes 发布系统。

这些属于专业工程团队的独立知识体系。FDE 在 Build 和 Scale 阶段更重要的任务是：

> **把已经验证的客户价值接入真实数据、真实系统、真实流程和真实责任体系，并让客户团队最终能够接管。**

因此，第 14 章需要从“通用生产运维知识”转回“FDE 客户现场交付”。

---

## 二、FDE 的 Build 与普通软件工程 Build 的区别

### 1. 普通软件工程 Build

普通软件工程更关注：

```text
需求实现
→ 开发测试
→ 部署上线
→ 稳定运行
```

核心问题是：

- 代码是否正确；
- 系统是否可靠；
- 服务是否可运维；
- 性能是否满足要求。

### 2. FDE 的 Build

FDE 的 Build 更强调：

```text
已验证的客户价值
→ 接入客户真实数据和系统
→ 嵌入客户业务流程
→ 对齐权限、责任和人工兜底
→ 形成客户可以验收的业务能力
```

它关注的不只是系统能否运行，而是原型进入客户现场后，原来的价值假设是否仍然成立。

| Prototype 状态 | FDE Build 要完成的转换 |
|---|---|
| 使用模拟数据 | 接入真实数据源并确认数据责任 |
| 独立 Demo | 嵌入客户现有业务流程 |
| 临时 API 或本地页面 | 对接客户身份、权限和业务系统 |
| 小样本技术指标 | 用真实业务口径验证 |
| 模型产生输出 | 输出进入业务动作并回写状态 |
| 开发者自己能跑 | 客户人员能够使用、审核和处理异常 |
| 演示结果 | 可被客户签收的业务能力 |

FDE Build 最关键的问题是：

> **Prototype 成立时依赖的假设，进入客户真实环境后还有多少成立？**

---

## 三、FDE 的 Scale 与通用技术扩容的区别

### 1. 通用技术 Scale

技术语境中的 Scale 通常关注：

- 增加实例；
- 扩大吞吐；
- 提升并发；
- 做高可用；
- 建设监控；
- 扩容存储和计算资源。

这些内容是 Scale 的技术基础，但不是 FDE Scale 的全部，也不应成为本章主体。

### 2. FDE 的 Scale

FDE Scale 更关注：

```text
一个场景跑通
→ 客户团队可以自行运营
→ 推广到更多部门或业务场景
→ 抽象出可复用对象、动作与工程机制
→ 回注平台
→ 下一个客户交付更快
```

建议将 Scale 区分为三个维度：

| Scale 维度 | 核心问题 | 主要责任 |
|---|---|---|
| 技术扩展 | 系统能否承载更大规模 | 平台、架构、运维团队主责，Delta 参与判断 |
| 客户自运营 | 客户离开 FDE 后能否继续使用和维护 | Delta 主导交接 |
| 能力复制 | 是否能复用于其他场景和客户 | Echo、Delta、Engineering 共同完成 |

本书第 14 章应重点教授后两项，对技术扩展只保留生产准入判断与团队协作接口。

## 六、建议的新章节结构

# 第 14 章　Delta 工作法：生产落地、客户接管与能力回注

## 本章导学

建议学习目标控制为 6 项：

1. 区分 Prototype、FDE Build 与 FDE Scale；
2. 验证 Demo 进入客户现场后的数据、流程、系统和责任假设；
3. 将模型输出接入真实业务动作和人工兜底；
4. 使用 FDE 生产准入 Gate 判断是否具备上线条件；
5. 完成客户自运营与接管演练，明确 FDE 撤出条件；
6. 识别并验证可回注的业务本体和工程机制。

---

## 14.1 从 Prototype 到客户环境：五个关键转换

用五个转换建立全章地图：

```text
模拟数据 → 真实数据
独立 Demo → 客户业务系统
模型输出 → 业务动作闭环
开发者运行 → 客户团队运营
客户定制 → 平台能力
```

### 14.1.1 模拟数据到真实数据

讲清：

- 原型数据与真实数据的分布差异；
- 真实字段缺失、格式不一致、历史数据错误；
- 数据由谁负责；
- 数据更新如何通知；
- 数据安全域是否发生变化；
- 原型指标能否在真实数据上复现。

### 14.1.2 独立 Demo 到客户系统

讲清：

- Demo 的入口在哪里；
- 需要调用哪些现有系统；
- 哪个系统是事实来源；
- 结果写回哪里；
- 用户继续使用旧账号还是新账号；
- 对接失败时业务如何继续。

### 14.1.3 模型输出到业务动作

讲清：

```text
模型输出
→ 业务规则
→ 权限判断
→ 人工确认
→ 系统动作
→ 状态回写
```

强调：

> 模型给出结果不等于业务动作已经完成；输出没有进入真实流程，就还没有完成 Build。

### 14.1.4 开发者运行到客户运营

讲清：

- 谁启动和停止服务；
- 谁处理失败请求；
- 谁维护知识和规则；
- 谁批准配置变更；
- 谁解释指标变化；
- 谁承担最终责任。

### 14.1.5 客户定制到平台能力

讲清：

- 哪些内容只能留在客户域内；
- 哪些对象、关系、动作和工程机制具有通用性；
- 如何避免把客户专属逻辑污染公共平台；
- 如何通过第二场景验证复用。

---

## 14.2 真实环境适配：验证原型假设

### 14.2.1 数据假设

需要核验：

- 数据是否真实存在；
- 字段含义是否一致；
- 数据质量是否支持当前方案；
- 数据是否及时更新；
- 数据是否可以在目标安全域中使用；
- 原型测试集是否代表真实业务分布。

### 14.2.2 系统假设

需要核验：

- 接口是否存在且稳定；
- 认证方式是否允许接入；
- 是否有调用频率限制；
- 是否支持结果回写；
- 是否存在旧系统兼容问题；
- 是否有测试环境或沙箱。

### 14.2.3 业务假设

需要核验：

- 业务规则是否有正式口径；
- 人工兜底是否有人承接；
- 原有流程是否允许改变；
- 业务人员是否接受新的职责；
- 验收指标是否仍被业务方认可。

### 14.2.4 责任假设

需要核验：

- 谁对模型输出负责；
- 谁处理错误和申诉；
- 谁批准高风险动作；
- 谁维护数据、政策和部门规则；
- 谁承担系统运行责任。

建议增加“原型假设核验表”：

| 原型假设 | 客户现场证据 | 是否成立 | 不成立的影响 | 调整动作 |
|---|---|---|---|---|

## 14.3 数据接入与业务语义对齐

这是 FDE Build 的核心工作之一，不应被简化为通用数据工程。

### 14.3.1 找到事实来源

对于每个关键数据，明确：

- 哪个系统是唯一事实来源；
- 是否存在多个冲突来源；
- 谁能解释字段含义；
- 数据延迟多长；
- 数据错误由谁修复。

### 14.3.2 对齐业务术语

同一概念可能在多个系统中有不同名称，例如：

- “诉求”“案件”“事件”“工单”是否是同一对象；
- “责任部门”和“承办部门”是否含义一致；
- “已处理”“已办结”“已关闭”是否处于同一状态。

Delta 不能自行猜测，应与 Echo、业务人员和系统负责人共同确认。

### 14.3.3 识别对象、关系、状态和动作

为后续本体回注收集：

- 核心业务对象；
- 对象属性；
- 对象之间的关系；
- 对象生命周期与状态；
- 可以执行的业务动作；
- 动作的权限和审批条件。

本节只完成业务语义对齐与候选收集；完整的业务通用性判断由第 15 章完成。

---

## 14.4 从模型结果到业务闭环

分别对三个 Demo 说明 Build 的真正完成标准：

| Demo | Prototype 结果 | 进入客户环境后必须闭合的动作 |
|---|---|---|
| 诉求分类器 | 输出分类标签 | 写回工单、低置信度进入人工队列、人工修正结果回流 |
| 政策 RAG | 输出答案和来源 | 引用可打开原文、文档版本可核对、政策更新后重新验证 |
| 路由工作流 | 输出处理分支 | 调用真实工具、进入审批、动作结果回写、失败可恢复 |

### 14.4.1 业务动作链

建议统一检查：

```text
输入来自哪里
→ 模型或规则做什么判断
→ 谁确认这个判断
→ 调用哪个业务动作
→ 动作结果写回哪里
→ 失败时停在哪里
→ 谁继续处理
```

### 14.4.2 人工兜底不是一个标签

“转人工”只有满足以下条件才算真实闭环：

- 有明确接收队列；
- 有负责人；
- 有处理时限；
- 人工可以看到必要上下文；
- 审核结果能够回写；
- 未处理任务会告警；
- 后续可以用于评测和改进。

### 14.4.3 状态回写与事实一致性

系统执行后必须明确：

- 哪个系统保存最终状态；
- 重复请求是否会造成重复动作；
- 写回失败如何恢复；
- 人工修改与 AI 建议冲突时以谁为准；
- 审计链是否保留。

## 14.5 FDE 生产准入 Gate

建议将当前九维 Build Readiness Gate 收敛为八项 FDE 生产准入条件：

| Gate | 核心问题 | 通过证据 |
|---|---|---|
| 数据接入 | 真实数据可用且责任清楚吗 | 数据样本、字段映射、质量报告 |
| 系统集成 | 输入、动作和状态回写接通了吗 | 接口联调记录、端到端演示 |
| 权限责任 | 谁能看、谁能改、谁批准清楚吗 | 权限矩阵、越权拒绝、责任确认 |
| 异常兜底 | 外部依赖失败后业务还能继续吗 | 故障演练、人工队列、恢复记录 |
| 过程追溯 | 能还原一次业务判断和动作吗 | 日志、审计、版本标识 |
| 发布回退 | 新版本退化时能恢复吗 | 灰度记录、回滚验证 |
| 客户接管 | 客户团队能独立运行吗 | 运行手册、接管演练 |
| 回注准备 | 能区分客户专属与通用能力吗 | 回注候选、隔离说明、复用证据 |

### Gate 判断格式

```text
当前状态
→ 客户现场证据
→ 未关闭风险
→ 修复或降级动作
→ 责任人
→ 是否允许进入下一阶段
```

### Gate 结果

应允许：

- 通过；
- 有条件通过；
- 继续试点；
- 返回 Prototype；
- 返回 Discovery；
- 停止。

不得为了按计划上线而把“未通过”写成“基本通过”。

## 14.6 客户现场的异常与变更

本节重点讲 FDE 现场变化，而不是通用错误码。

### 14.6.1 常见现场变化

- 客户字段或接口改变；
- 部门职责调整；
- 政策文件更新；
- 验收口径发生变化；
- 客户临时扩大范围；
- 一线人员拒绝使用；
- 原系统接口不稳定；
- 合规要求提高；
- 客户负责人更换；
- 人工审核容量不足。

### 14.6.2 处理分级

遇到现场变化时，Delta 不应默认继续加代码，应判断：

| 处理方式 | 适用情况 |
|---|---|
| 临时修复 | 紧急恢复，不改变业务边界 |
| 配置调整 | 变化属于已设计的配置范围 |
| 通用组件修改 | 多场景存在同类需求，值得工程回注 |
| 返回 Prototype | 技术方案或指标需要重新验证 |
| 返回 Discovery | 业务问题、用户或价值假设发生变化 |
| 停止 | 风险、成本或价值已不成立 |

### 14.6.3 变更不能绕过 Echo

以下情况必须重新让 Echo 参与判断：

- 客户改变目标用户；
- 业务成功标准变化；
- 自动化边界扩大；
- 人工责任发生变化；
- 方案影响新的监管要求；
- 原快赢场景不再有价值。

这体现 Echo 与 Delta 在 Build 阶段并非完全割裂。

## 14.7 生产保障：FDE 必须会判断，但不必包办实现

本节压缩现有通用运维内容，统一写成“生产准入证据”。

### 14.7.1 配置与密钥

FDE 必须确认：

- 配置与代码分离；
- Secret 不进入源码、日志和交付包；
- 环境之间不会误用配置；
- 缺少必要配置时安全失败。

底层密钥平台由客户安全或平台团队负责时，FDE 应明确接口和责任，不必自行建设一套密钥系统。

### 14.7.2 日志、审计与指标

FDE 必须确认系统能回答：

- 发生了什么；
- 谁作出了什么操作；
- 当时使用什么模型、Prompt、配置和数据版本；
- 系统现在是否处于异常状态。

具体监控平台可由客户既有系统承载。

### 14.7.3 超时、重试与安全降级

FDE 必须定义业务行为：

- 失败后是否重试；
- 重试是否可能造成重复业务动作；
- 什么时候停止自动处理；
- 什么时候进入人工；
- 谁处理积压任务。

### 14.7.4 权限与动作边界

FDE 必须确认：

- 模型可以建议什么；
- 模型可以执行什么；
- 哪些动作必须人工批准；
- 哪些动作不得自动执行；
- 操作是否可追责。

### 14.7.5 灰度、回滚与监控

FDE 必须要求：

- 新版本先小范围验证；
- 退化后可切回稳定版本；
- 关键业务指标和异常可见；
- 告警有负责人和处置动作。

具体发布平台和监控工具不作为本章主线教学内容。

---

## 14.8 客户自运营与 FDE 撤出

### 14.8.1 客户自运营需要哪些角色

至少明确：

- 业务 owner；
- 技术 owner；
- 数据 owner；
- 人工审核负责人；
- 安全与合规负责人；
- 事故升级联系人。

### 14.8.2 客户需要掌握哪些操作

- 启动和健康检查；
- 查看业务和系统状态；
- 处理人工任务；
- 更新政策、标签或配置；
- 处理常见故障；
- 版本切换和回滚；
- 发起变更审批。

### 14.8.3 接管演练

保留并强化跨组接管：

> 接管组不能询问原作者，只能依据运行手册和交接材料完成启动、处理一个预设异常、确认业务状态并恢复服务。

### 14.8.4 FDE 撤出条件

建议明确：

- 客户 owner 已确认；
- 日常操作已培训；
- 常见故障可独立处理；
- 人工审核队列有人负责；
- 关键指标有人查看；
- 版本变更有审批流程；
- 支持边界和升级渠道已确认；
- 未关闭风险已书面接受；
- 客户在限定观察期内完成独立运行。

Scale 的完成标志不是“FDE 一直驻场保证系统运行”，而是客户对日常运营的依赖逐步下降。

## 14.9 工程能力回注与业务本体

### 14.9.1 两类回注对象

| 回注类型 | 典型内容 | 判断重点 |
|---|---|---|
| 工程能力 | 配置、provider 适配、审计、失败兜底、健康检查、交接模板 | 能否跨 Demo 复用 |
| 业务语义候选 | 对象、关系、状态、动作和权限 | 能否跨客户解释和执行 |

第 14 章负责工程可执行性，第 15 章负责业务通用性和价值判断。

### 14.9.2 Palantir Ontology 的参考意义

Palantir Ontology 可以作为业务语义回注的代表性实现：

- 对象和属性描述业务世界中有什么；
- 关系描述对象如何关联；
- 动作和函数描述业务可以做什么；
- 权限与治理约束谁可以执行。

本书借鉴这种方法，但不要求使用特定平台。

### 14.9.3 本体工程验证

Delta 需要验证：

- 对象属性有稳定数据来源；
- 对象身份可以唯一确认；
- 关系有维护机制；
- 状态变化有合法路径；
- 动作有真实接口或人工流程；
- 权限、审计和失败处理可验证；
- 客户专属数据没有进入公共平台；
- 至少一个对象或动作模型在第二个场景复用。

### 14.9.4 成熟度区分

```text
概念本体
→ 已定义对象、关系和动作

可执行本体
→ 已映射数据、接口、权限和状态

已验证回注能力
→ 已在第二场景完成复用验证
```

不得把一张对象关系图直接称为平台能力。

## 14.10 贯穿实操：把一个 Demo 接入模拟客户环境

### 1. 实操定位

本实验不要求学员搭建完整生产基础设施，而是模拟 FDE 把 Demo 接入客户现场的全过程。

### 2. 默认对象

建议使用第 8 章诉求分类器，原因是：

- 业务逻辑较简单；
- 依赖较少；
- 便于观察业务接入和接管；
- 不会让课堂重新陷入 RAG 或 Agent 调试。

进阶组可以选择第 12 章路由工作流。

### 3. 模拟客户环境应提供

- 一份与原测试集格式不同的“客户真实格式”数据；
- 一个模拟工单接口；
- 一个用户与角色清单；
- 一个人工审核队列；
- 一次字段变更；
- 一次接口失败；
- 一份客户接管要求；
- 一个用于验证复用的第二场景。

### 4. 实操步骤

#### 环节一：核验原型假设

- 对比模拟数据和客户数据格式；
- 找出字段、类别和数据质量差异；
- 确认哪些原型指标不能直接沿用；
- 更新方案边界。

#### 环节二：接入客户数据和系统

- 建立字段映射；
- 调用模拟工单接口；
- 将分类结果写回；
- 记录事实来源和状态。

#### 环节三：闭合人工兜底

- 低置信度结果进入人工队列；
- 审核人员可以查看上下文；
- 审核结果写回；
- 超时未处理会产生提醒。

#### 环节四：处理现场变化

注入以下变化之一：

- 新增部门类别；
- 字段名称改变；
- 模拟接口暂时失败；
- 验收口径变化；
- 合规要求提升。

学员判断应当：

- 改配置；
- 改通用组件；
- 返回 Prototype；
- 返回 Discovery；
- 或停止。

#### 环节五：完成生产准入评审

按八项 Gate 逐项给出：

- 现场证据；
- 未关闭风险；
- 是否允许进入下一阶段；
- 责任人和条件。

#### 环节六：跨组接管

接管组仅依靠运行与业务说明完成：

- 启动；
- 处理一条正常诉求；
- 处理一条人工审核诉求；
- 处理一个接口异常；
- 确认状态回写；
- 恢复服务。

#### 环节七：能力回注

- 抽象一个工程机制；
- 抽象一个对象或动作模型；
- 在第二场景中尝试复用；
- 记录需要修改的内容；
- 判断属于客户定制、回注候选还是已验证能力。

### 5. 实操最终认知

```text
Demo 能跑
≠
进入客户业务

进入客户业务
≠
客户能够接管

客户能够接管
≠
能力已经可以跨客户复用
```

### 核心必做

所有学员完成：

1. 原型假设核验；

## 八、建议增加的 FDE 现场案例

### 案例一：字段语义不一致

工单系统的“类别”表示责任部门，数据平台的“类别”表示事件性质。Delta 如果只按字段名对接，分类结果会写入错误位置。

**教学点：** 数据接入首先是业务语义对齐，不是接口调用。

### 案例二：模型判断正确，业务动作失败

分类器正确判断为住建，但工单系统接口超时，工单没有真正分派。

**教学点：** 模型指标正确不等于业务闭环完成。

### 案例三：转人工没有接收人

系统输出“转人工”，但没有人工队列、负责人和处理时限。

**教学点：** 人工兜底必须进入真实流程，不能只是一个标签。

### 案例四：部门职责调整

客户将一类事项从住建调整到城管。如果逻辑写死在 Prompt 和代码中，修改困难且无法追溯。

**教学点：** 现场变化应优先通过配置和业务模型处理；超出原问题边界时应返回 Discovery。

### 案例五：客户离不开原作者

系统上线后，每次改阈值和排障都要找原 Delta。

**教学点：** FDE 长期驻场不是 Scale 成功；客户能够自运营才是。

### 案例六：代码可复用，业务语义不可复用

分类代码可以复制到企业员工服务台，但“住建、人社、市监、城管”完全不适用。

**教学点：** 回注应区分客户内容、通用对象结构和通用工程机制。

## 九、各节统一写作模板

为避免重新写成条目式检查清单，每个核心小节建议包含：

1. **客户现场问题**：真实交付中为什么会发生；
2. **FDE 判断**：Delta 需要判断什么；
3. **协作边界**：哪些由 Delta 完成，哪些交给平台、安全、运维或 Echo；
4. **西岭例子**：在贯穿案例中怎样表现；
5. **反模式**：常见错误和业务后果；
6. **轻量操作**：学员亲手做什么；
7. **验收证据**：怎样证明完成；
8. **迁移问题**：换成 RAG、路由或第二客户有何变化。

每一节都应回答：

> **这件事为什么是 FDE 在客户现场必须关心的，而不是一段通用运维知识？**

无法回答这个问题的内容，应移入附录或资源包。

## 十、建议的新反模式与红线

- **把 Build 理解成“把 Demo 部署到服务器”。** 没有真实数据、系统接口、业务动作和责任闭环，就没有完成 Build。
- **只验模型输出，不验业务动作。** 分类正确但未写回、路由正确但未进入队列，都不算业务闭环。
- **用技术补丁掩盖需求变化。** 目标用户、价值指标或责任边界变化时，应返回 Discovery，而不是继续加代码。
- **把“转人工”写成一个标签。** 没有队列、负责人、时限和回写，就没有人工兜底。
- **把客户现有平台工作全部揽给 FDE。** FDE 应定义准入条件和协作接口，不应取代客户的安全、运维和平台团队。
- **把永久驻场当成 Scale。** 客户始终离不开原作者，说明交接失败。
- **把客户内容回注公共平台。** 回注结构、动作和机制，不回注客户数据与专属政策。
- **把对象关系图当平台能力。** 未完成数据、动作、权限和第二场景验证，只能称为概念模型。
- **为了按计划上线而放宽 Gate。** 未通过是正常结果，掩盖风险才是失败。
