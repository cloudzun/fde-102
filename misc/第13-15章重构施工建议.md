# 第 13—15 章重构施工建议

> **文档用途：** 供教材编写组执行第 13—15 章重构  
> **依据版本：** 教科书 v0.7  
> **涉及范围：** 第 13 章、第 14 章、新增 Build & Scale 章节，以及原第 15 章实操五的顺延联动  
> **核心原则：** 第 13、14 章属于 Delta 能力线；第 15 章属于 Echo 能力线；最终综合实操由 Echo 与 Delta 共同完成。

---

## 一、重构结论

### 1. 推荐结构

建议在现有第 13 章与第 14 章之间，新增一章专门面向 Delta 的 Build & Scale 章节，并将现有第 14、15 章依次顺延：

| 新章号 | 建议标题 | 主导角色 | 核心问题 |
|---|---|---|---|
| 第 13 章 | 企业私有化部署与模型适配 | Delta | 生产底座部署在哪里，模型如何适配 |
| 第 14 章 | Delta 工作法：Build、Scale 与工程化交付 | Delta | Demo 怎样变成可运行、可恢复、可交接的系统 |
| 第 15 章 | Echo 工作法：价值落地、组织采纳与能力回注 | Echo 主导，Delta 提供证据 | 系统为什么值得采用，组织如何推广，哪些能力值得回注 |
| 第 16 章 | 实操五：全团队交付、Go/No-Go 与决策层汇报 | Echo + Delta | 综合工程与业务证据，决定上线、继续试点或停止 |

### 2. 三章叙事关系

```text
第 13 章：生产技术底座怎么选
        ↓
第 14 章：系统怎样接得住
        ↓
第 15 章：组织为什么愿意接
        ↓
第 16 章：全团队作出最终交付决策
```

### 3. 能力边界

| 章节 | 负责回答 | 不负责回答 |
|---|---|---|
| 第 13 章 | 部署形态、模型选择、容量、模型适配和评测 | 应用的完整运行与运维体系 |
| 第 14 章 | 配置、日志、审计、稳定性、权限、发布、回滚、监控和技术接管 | 客户为何采用、ROI 是否成立 |
| 第 15 章 | 价值证据、组织采用、干系人沟通和回注判断 | 具体技术运维实现 |

### 4. 两种 Scale 的区分

| Scale 维度 | 核心问题 | 主导角色 | 所属章节 |
|---|---|---|---|
| 工程 Scale | 系统能否稳定运行、监控、恢复并由客户技术团队接管 | Delta | 第 14 章 |
| 业务 Scale | 组织是否愿意采用、推广，价值是否成立 | Echo | 第 15 章 |

两者共同构成完整 Scale：

> **Delta 让系统接得住，Echo 让组织愿意接。**

# 二、第 13 章修订建议

## 1. 建议标题

# 第 13 章　企业私有化部署与模型适配

建议将原题中的“模型微调”调整为“模型适配”。

“模型适配”覆盖的解决方案包括：

- 更换基础模型；
- Prompt 优化；
- 结构化输出；
- RAG 或外部工具；
- 规则与校验器；
- LoRA / QLoRA；
- 部署方式和推理引擎调整。

这样可以避免把微调误写成私有化部署或高级项目的必经步骤。

## 2. 本章定位

本章是 Delta 的生产技术专题，回答系统进入 Build 前的两个问题：

1. 生产环境部署在哪里；
2. 现有模型能力是否足以满足业务要求，若不足应如何适配。

本章负责技术底座选择，但不展开完整的应用运维体系。配置、日志、审计、熔断、灰度、监控和交接统一放入第 14 章。

## 3. 建议学习目标

完成本章后，学员应能够：

1. 根据数据分类、网络边界和监管要求定义项目安全域；
2. 在公网 API、专属实例、私有云和本地机房之间选择部署形态；
3. 根据模型能力、许可证、推理引擎、硬件资源和并发要求形成部署初案；
4. 进行容量初筛，并说明估算假设和实测要求；
5. 区分 Prompt、结构化输出、RAG、规则、模型替换和微调的适用边界；
6. 建立模型适配的数据治理、对照评测、灰度和回滚 Gate；
7. 为第 14 章工程化施工形成明确的生产技术底座决策。

## 4. 建议章节结构

### 13.1 从原型环境进入生产环境

说明 Prototype 与生产环境约束的变化：

- 数据是否可以出域；
- 网络是否可以访问公网；
- 并发、延迟和吞吐要求；
- 服务可用性和恢复要求；
- 模型与软硬件兼容性；
- 客户运维能力；
- 合规、审计和供应链要求。

建议给出决策表：

| 判断项 | 需要回答的问题 | 产生的决策 |
|---|---|---|
| 数据属性 | 是否包含个人信息、敏感信息、内部知识 | 数据处理边界 |
| 网络边界 | 能否访问公网、能否跨区域 | 部署区域和服务形态 |
| 模型要求 | 是否允许闭源 API、是否需要开源权重 | 模型来源 |
| 性能要求 | 并发、延迟、上下文、吞吐是多少 | 模型规格和硬件 |
| 运维能力 | 客户能否维护 GPU 和推理服务 | 托管或自建 |
| 信创要求 | 是否有指定软硬件目录 | 芯片、操作系统和数据库 |

### 13.2 私有化部署的四种形态

区分以下四种形态：

1. 公网 API；
2. 专属实例或隔离 VPC；
3. 客户私有云；
4. 完全离线的本地机房或一体机。

每种形态统一讲解：

- 数据流向；
- 网络边界；
- 运维责任；
- 成本结构；
- 交付速度；
- 可控性；
- 合规适用边界。

不得再把“私有化”简单等同于“客户本地机房”。

### 13.3 模型与推理底座选型

正文讲稳定的决策逻辑：

```text
任务要求
→ 数据与网络边界
→ 模型能力
→ 权重与许可证
→ 推理引擎兼容性
→ 芯片和容量
→ 吞吐、延迟与成本
→ 运维条件
```

具体模型、芯片、版本和价格放入动态速查或附录，并注明来源和核验时间，不作为正文稳定主干。

### 13.4 容量估算与实测

修正“参数量直接等于卡数”的简单推导。

建议给出容量初筛框架：

```text
推理资源需求
=
模型权重
+ KV Cache
+ 激活与运行时缓冲
+ 并发余量
+ 框架与通信开销
```

训练或微调还需考虑：

```text
梯度
+ 优化器状态
+ 激活保存
+ 通信与分布式开销
```

必须强调：

> 容量公式只用于初筛，最终结论必须来自目标模型、目标上下文长度、目标并发、目标精度和目标推理引擎的实测。

### 13.5 模型适配决策

建议采用以下决策顺序：

```text
基础模型评测
→ Prompt 与结构化输出
→ RAG 或外部工具
→ 规则和校验器
→ 更换模型
→ LoRA / QLoRA
→ 极少数情况下考虑全参微调
```

建议增加组合决策表：

| 问题 | 优先方案 |
|---|---|
| 知识经常变化且需要引用 | RAG |
| 输出格式不稳定 | Prompt、Schema、校验器 |
| 固定行业表达或行为模式 | 可评估 LoRA |
| 需要执行动作 | Workflow / Agentic Workflow |
| 基础能力不足 | 优先比较和更换模型 |
| 同时需要知识与行为适配 | RAG + LoRA 等组合 |

“RAG 管事实、微调管行为”只能作为默认启发式，不能写成绝对规律。

### 13.6 微调的数据治理与评测 Gate

在微调流程之前增加 Data Gate：

- 数据是否获得授权；
- 是否包含个人信息或敏感信息；
- 是否需要脱敏；
- 是否存在版权和客户隔离要求；
- 是否存在重复样本；
- 训练集、开发集和盲测集是否隔离；
- 数据版本、哈希和血缘是否记录；
- 是否支持删除、追溯和回滚。

评测至少比较：

```text
基础模型
vs
LoRA Adapter
vs
合并后的模型
vs
量化后的生产模型
```

评测维度至少包括：

- 目标任务；
- 通用能力回归；
- 安全与拒答；
- 格式稳定性；
- 性能与成本。

### 13.7 小模型 QLoRA 实验

保留 v0.7 已增加的小模型 QLoRA 实验，但应明确其教学目的：

- 体验数据准备；
- 建立训练、开发、盲测隔离；
- 理解 Adapter 产物；
- 对比微调前后效果；
- 检查通用能力退化；
- 理解 Adapter 独立加载与合并部署；
- 完成回滚验证。

本实验不以训练强模型为目标，也不以大型旗舰模型或多卡集群为前提。

### 13.8 本章总结：生产技术底座决策

本章结尾应形成一张可直接用于实际项目的决策检查表，覆盖：

- 安全域；
- 部署形态；
- 模型和推理引擎；
- 容量假设；
- 模型适配方案；
- 数据治理；
- 评测、灰度和回滚条件。

不必要求学员创建一组额外项目文件，重点是让读者形成完整的技术判断框架。

## 5. 第 13 章验收标准

- [ ] 有基础模型与适配模型的对照评测；
- [ ] 有灰度和回滚思路；
- [ ] 结论足以支持第 14 章继续进行工程化设计。

# 三、新增第 14 章施工建议

## 1. 建议标题

# 第 14 章　Delta 工作法：Build、Scale 与工程化交付

## 2. 本章定位

本章是 Delta 侧生产化实战单元。学员从第 8、10、12 章选择一个 Demo，把它从“演示可行”推进到“可运行、可观察、可恢复、可交接”的工程状态。

本章核心不是介绍某个运维平台，而是建立以下判断：

> 系统出问题时是否可控，客户技术团队能否在不依赖原作者的情况下接管。

## 3. 建议学习目标

完成本章后，学员应能够：

1. 区分 Prototype、Build 和工程 Scale 所需证据；
2. 使用 Build Readiness Gate 识别生产差距；
3. 完成配置、Secret、日志、审计和指标建设；
4. 设计并验证超时、重试、熔断和安全降级；
5. 建立权限与最小权限模型；
6. 管理代码、模型、Prompt、配置、数据和索引版本；
7. 完成一次灰度发布、异常回滚和监控告警；
8. 编写运行手册，并通过跨组接管验证其有效性；
9. 识别可跨 Demo 复用的工程能力。

## 4. 实验对象建议

### 默认路径：第 8 章分类器

推荐原因：

- 业务逻辑简单；
- 环境依赖较少；
- 便于模拟超时、错误和版本变化；
- 学员可以把注意力放在生产纪律，而不是重新调试业务功能。

### 进阶路径：第 12 章路由工作流

可以增加：

- 工具调用失败；
- 人工审批；
- 状态持久化；
- 动作幂等；
- 工具权限；
- 审计链。

### 不建议把 RAG 作为默认对象

RAG 的文档解析、embedding、索引和生成环节较多，容易使课堂重新陷入功能调试，偏离 Build / Scale 教学目标。

## 5. 建议章节结构

### 14.1 Prototype、Build 与 Scale 的证据边界

| 阶段 | 核心问题 | 判断依据 |
|---|---|---|
| Prototype | 方案能不能成立 | 功能 Demo、小样本验证 |
| Build | 系统能不能稳定、安全地运行 | 测试、异常恢复、权限、版本和回滚 |
| 工程 Scale | 客户技术团队能不能持续运营 | 监控、告警、运行手册和接管演练 |

核心结论：

> Prototype 证明能做，Build 证明能稳定运行，工程 Scale 证明客户技术团队能够接管。

### 14.2 Build Readiness Gate

设置八个生产准备维度：

1. 功能与数据；
2. 配置与密钥；
3. 性能与容量；
4. 稳定性与降级；
5. 权限与安全；
6. 日志、审计与指标；
7. 发布、灰度与回滚；
8. 运维与交接。

统一判断格式：

```text
当前状态
→ 生产差距
→ 修复动作
→ 责任人
→ 完成证据
→ 未通过时的处理
```

### 14.3 配置与密钥管理

讲解并实际验证：

- 配置与代码分离；
- 开发、测试和生产环境分离；
- Secret 不进入源码、日志和版本库；
- 模型、provider、Prompt 和阈值可配置；
- 缺少必需配置时安全失败。

实验应删除必要配置后启动系统，验证系统拒绝启动并给出明确错误，而不是带着错误配置继续运行。

### 14.4 日志、审计与指标

明确区分：

- **日志：** 系统发生了什么；
- **审计：** 谁在何时使用哪个版本做了什么决定；
- **指标：** 系统当前运行得怎么样。

日志至少包含：

- `request_id`；
- 请求时间；
- 处理结果；
- 延迟；
- 异常类型；
- 模型、Prompt 和配置版本；
- 是否转人工。

不得记录明文个人信息和密钥。

指标至少包括：

- 请求量；
- 成功率和错误率；
- P50 / P95 延迟；
- 模型调用失败率；
- 转人工率或拒答率；
- 类别分布；
- token 或调用成本；
- 场景质量指标。

必须实际运行样本并查看指标，不能只提交设计说明。

### 14.5 超时、重试、熔断与降级

通过故障注入覆盖：

- API 超时；
- 429 限流；
- 500 服务错误；
- JSON 字段缺失；
- 连续失败。

系统行为应遵循：

```text
短暂故障 → 有限次数重试
连续故障 → 熔断或暂停调用
不可恢复故障 → 安全降级或转人工
```

必须明确：

- 最大重试次数；
- 退避策略；
- 总超时时间；
- 熔断触发条件；
- 恢复条件；
- 降级输出。

禁止无限重试，也不得在失败时编造答案或默认自动处理。

### 14.6 权限与最小权限

建议至少区分：

| 角色 | 允许操作 | 禁止操作 |
|---|---|---|
| 普通业务用户 | 提交请求、查看本次结果 | 修改 Prompt、阈值和模型配置 |
| 人工审核员 | 处理人工升级、查看审核记录 | 修改代码、删除审计记录 |
| 系统管理员 | 修改配置、查看全量指标 | 绕过审计修改历史记录 |
| 审计人员 | 只读查看审计记录 | 执行业务操作和修改配置 |

实验中必须实际用普通用户尝试调用管理功能，验证：

- 请求被拒绝；
- 拒绝行为进入审计日志；
- 不泄露敏感配置。

### 14.7 版本、灰度与回滚

统一管理：

- 代码版本；
- 模型或 provider 版本；
- Prompt 版本；
- 配置版本；
- 数据集版本；
- RAG 场景的索引版本。

轻量实验流程：

1. 运行稳定版 v1；
2. 创建修改后的 v2；
3. 将少部分测试请求分配给 v2；
4. 比较质量、延迟和成本；
5. 人为制造 v2 退化；
6. 执行回滚；
7. 验证 v1 恢复。

不要求引入 Kubernetes，可使用双配置、双进程或测试脚本完成。教学重点是发布纪律，不是基础设施平台。

### 14.8 监控告警与事故响应

至少建立三类告警：

- 错误率持续超过阈值；
- P95 延迟异常；
- 转人工率、拒答率或类别分布异常。

必须实际触发至少一次告警，并记录：

- 告警接收人；
- 响应时间；
- 排查过程；
- 是否回滚；
- 恢复验证；
- 事故复盘。

### 14.9 运行手册与客户技术团队接管

运行手册至少应说明：

- 启动、停止和健康检查；
- 日志和指标位置；
- 常见故障处理；
- 配置修改流程；
- 版本切换和回滚；
- 人工升级条件；
- 责任人与升级路径。

安排跨组接管演练：

> 接管组不能询问原作者，只能依据运行手册完成系统启动、故障定位、版本回滚和服务恢复。

必须明确：

```text
原团队能运行
≠
客户团队能接管

客户团队不依赖原作者也能运行
才说明具备工程 Scale 条件
```

### 14.10 工程能力回注

本节只讨论 Delta 侧工程复用，例如：

- 配置加载模块；
- provider 适配层；
- 日志和审计组件；
- 重试与熔断组件；
- 健康检查；
- 版本清单；
- 告警规则；
- 运行手册模板。

至少选择一个工程机制在第二个 Demo 中复用，证明它不是仅适用于分类器的定制实现。

## 6. 第 14 章完成标准

## 4. 建议章节结构

### 15.1 从“系统能运行”到“组织愿意采用”

开篇明确：


建立两个区别：

- 工程验收通过，不等于业务价值已经成立；
- 业务价值成立，不等于组织一定愿意采用。

### 15.2 价值证据链

建立完整链条：

```text
业务痛点
→ 当前基线
→ 系统能力
→ 技术指标
→ 业务变化
→ 可量化价值
```

以分类器为例：

```text
错分返工
→ 当前错分率和返工工时
→ 自动分类 + 低置信度转人工
→ 盲测准确率、覆盖率、转人工率
→ 返工减少、处理时间下降
→ 年度净收益和服务质量改善
```

禁止从“准确率达到某个数字”直接跳到“每年节省多少成本”。

### 15.3 年度价值、净收益、ROI、TCO 与回收期

统一口径：

```text
年度价值
= 效率收益 + 质量收益 + 风险避免收益

年净收益
= 年度价值 − 年运营增量成本

TCO
= 建设成本 + 运行成本 + 维护成本 + 人工审核成本

ROI
=（累计收益 − 总投入）/ 总投入

投资回收期
= 总投入 / 月净收益
```

所有数字必须标记为：

- 已实测；
- 客户确认；
- 教学假设；
- 待验证。

对外汇报应提供区间与假设，不使用未经验证的单点承诺。

### 15.4 组织采用：门槛、动机与信任

保留现有框架，并与第 14 章工程证据建立联系：

| 采用障碍 | Echo 的策略 | Delta 提供的证据 |
|---|---|---|
| 门槛高 | 简化流程、设计试点 | 运行稳定性与操作手册 |
| 动机弱 | 证明个人和部门收益 | 使用时长与工作量变化 |
| 信任低 | 明确责任、人工兜底和回滚 | 审计、HITL、回滚报告 |
| 合规担忧 | 主动预审、明确安全域 | 权限、部署和审计证据 |
| 运维担忧 | 证明客户团队能接管 | 跨组接管报告 |

Echo 的表达必须建立在 Delta 已提供的工程证据上，不能只给口头承诺。

### 15.5 面向四类干系人的表达

| 干系人 | 核心关切 | 主要证据 |
|---|---|---|
| 决策层 | 值不值得、何时见效 | 年度价值、ROI、回收期、剩余风险 |

### 15.6 业务 Scale：试点、采用与推广

新增以下内容：

- 种子用户；
- 试点范围；
- 推广节奏；
- 培训计划；

形成业务 Scale 路径：

```text
小范围试点
→ 真实数据验证
→ 采用与业务指标复核
→ 扩大范围
→ 客户自运营
```

建议使用以下维度：

| 判断维度 | 核心问题 |
|---|---|

# 七、施工红线

1. **不把第 15 章写成项目文件清单。** 它是 Echo 知识章，重点是价值判断和组织采用的方法。
2. **不把 Build / Scale 写成运维名词百科。** 第 14 章必须围绕一个 Demo 做真实纵切。
3. **不引入复杂基础设施作为教学目标。** 默认不要求 Kubernetes、高可用集群或完整云平台。
4. **不把演示数据结论外推为生产保证。** 所有实测结论标注样本和环境边界。
5. **不把工程 Scale 和业务 Scale 混写。** 第 14 章由 Delta 主导，第 15 章由 Echo 主导。
6. **不把能力回注归给单一角色。** Echo 判断业务通用性，Delta证明工程复用性。
7. **不先写死实验命令。** 在重新审查实验环境前，只确定实验目标、证据和验收；环境复核后再补精确命令。
8. **不改变既有 Mermaid 图的方向、配色和节点文字，除非该图因章节重构必须新建或用户另行批准。**
9. **不遗漏章号顺延影响。** 新增第 14 章后，原第 14、15 章及其全部交叉引用必须同步更新。
