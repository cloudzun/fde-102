# gstack 标准开发流程

**版本**：V1（基于 AI Coding 企业实战训练营的实战经验总结）
**适用范围**：任何使用 gstack + OpenCode（或其他兼容工具）进行 AI 辅助开发的团队

---

## 流程总览

gstack 将一次完整的开发迭代组织为八个环节的流水线。上一环的产出是下一环的输入，没有环节可以被跳过。

```
office-hours → spec → autoplan → 施工 → review → qa → ship → retro
（要不要做） （做什么） （怎么拍板） （做出来） （找隐患） （测体验） （规范化收尾） （复盘改进）
```

**关键原则**：

- **不是所有改动都需要走完整流程**。部署配置、小范围文案调整等操作性工作，用提示词直接驱动即可。是否走完整流程的判断标准见下文"流程启动判断"。
- **每一环的产出物都是文件**（Markdown 文档），不是口头结论。这保证了团队协作时可追溯、可复用。
- **人的角色在每一环都不同**：office-hours 里人是提问者，spec 里人是追问者，autoplan 里人是决策者，review 里人是审查者——但**在任何环节，人的判断都是不可替代的**。

---

## 流程启动判断

在启动完整流程之前，先回答三个问题：

| 问题 | 如果答案是"是" | 如果答案是"否" |
|------|--------------|--------------|
| 这次改动如果做错了，代价大不大？ | 走完整流程 | 轻量处理即可 |
| 会不会有别人（同事、客户）用到它、依赖它？ | 走完整流程 | 轻量处理即可 |
| 它会不会长期存在、需要以后维护？ | 走完整流程 | 轻量处理即可 |

更具体的判断标准——以下五类改动**强烈建议走完整流程**：

- 触及数据模型（新增/修改数据库表结构）
- 触及接口契约（新增/修改 API 端点）
- 触及安全边界（认证、权限、输入校验）
- 需要多文件协同改动（前后端同时改）
- 涉及破坏性变更（会让老功能或老测试失效）

以下场景**不需要走完整流程**，用提示词驱动即可：

- 部署配置文件生成（已经做完选型判断之后）
- 纯文案/样式微调（不涉及逻辑变更）
- 补文档、补注释
- 一次性验证类的小脚本

## 环节一：office-hours — 想清楚该不该做

**目标**：在动手之前，先确认"这个需求值不值得投入开发资源"。

**操作步骤**：

1. 加载 `/office-hours` 技能
2. 用一句话描述你遇到的问题或想做的功能
3. AI 会通过一系列问题帮你审视这个想法的合理性和范围

**关键检查点**：

- 这个需求有没有"框架错位"——即你描述的解决方案和你真正想解决的问题之间存在鸿沟。如果有，office-hours 会追问出来
- 需求的边界是否清晰——什么该做、什么不该做
- 有没有更简单的替代方案可以先用

**产出物**：一份 office-hours 对话记录（或总结），核心结论是"继续往下走"或"先不做了/换个方向"

**常见错误**：

- 跳过这一步直接进入 spec——当需求本身有问题时，后面的所有工作都在一个错误的基座上搭建
- 把 office-hours 当成需求评审——它只判断"该不该做"，不判断"怎么做"

---

## 环节二：spec — 把需求死磕成精确规格

**目标**：把一句模糊的需求描述，变成一份经得起追问的、精确的技术规格。

**操作步骤**：

1. 加载 `/spec` 技能，输入 office-hours 确认后的需求（或轻量 PRD）
2. spec 会进行"死磕式"追问——它会主动问以下类型的问题：
   - "这个功能失败了怎么办？"
   - "如果两个人同时操作会怎样？"
   - "数据怎么存、存哪里？"
   - "有哪些明确的硬边界（绝对不能做的事）？"
3. 逐条回答 spec 的追问，直到规格完整

**关键检查点**：

- 正常路径之外，失败路径是否也被覆盖了？
- 边界情况（空输入、极端值、并发操作）是否被追问过？
- 数据模型是否明确（表结构、字段类型、约束）？
- "明确不做的范围"是否写清楚了？

**产出物**：一份 SPEC.md 文件，内容通常包括：功能概述、数据模型、API 设计、校验逻辑、硬边界（No-Gos）、以及对每个功能点的失败模式分析。

**常见错误**：

- 把 spec 当成"轻量 PRD 的扩写"——spec 的核心价值是**追问边界**，不是把已有的需求写得更长
- 对 spec 的追问敷衍了事——"应该没问题吧"不能作为回答，每个追问都要给出明确的结论
- 跳过失败模式的思考——正常路径最容易描述，但出错的往往是不正常的那条路径

---

## 环节三：autoplan — 把关键决策提前到动代码之前

**目标**：在执行之前，把那些"做完才发现不对、返工很贵"的品味决策提前拍板。

**操作步骤**：

1. 加载 `/autoplan` 技能，输入 spec 产出的 SPEC.md
2. autoplan 会识别出 spec 中没有明确规定、但在实现时需要做出选择的两可决策
3. 对每个决策，autoplan 给出选项和各自的利弊，由**人来拍板**——autoplan 只负责识别决策点，不替人做决定

**典型的决策类型**：

- 技术选型层面的两可选择（如"密码哈希用 bcrypt 还是 scrypt"）
- 架构层面的品味选择（如"脱敏该放在前端做还是服务端做"）
- 范围层面的取舍（如"这个功能是现在就做还是留到下一版"）
- 交互层面的体验选择（如"购物车是独立页面还是右侧抽屉"）

**关键检查点**：

- autoplan 识别的每一个决策点，是否都有人明确拍板？
- 拍板结论是否写进了 spec（更新 SPEC.md）作为后续施工的依据？

**产出物**：一份决策记录（可以在 SPEC.md 中追加"决策记录"章节，或单独保存），每一条包含：决策问题、可选方案、最终选择、选择理由。

**常见错误**：

- 把 autoplan 的"推荐"当成了"决定"——autoplan 只是列出选项和利弊，**最终拍板权永远是人的**，不能被自动化
- 跳过了需要讨论的决策——当两个方案各有道理时，不要因为赶时间顺手选一个，你现在随便选的那个很可能就是等下返工的原因

---

## 环节四：施工 — 照着规格写代码

**目标**：按照 SPEC.md 中已经过追问、拍板完成的精确规格，让 AI 生成代码。

**操作步骤**：

1. 确保 SPEC.md 和决策记录都在手边
2. 用提示词引导 AI 按顺序实现——先数据模型、再服务端逻辑、再前端页面
3. 每完成一个模块，跑对应的测试验证

**关键检查点**：

- 施工过程中有没有偏离 spec 里已经定好的约束？
- AI 有没有"顺手"做了 spec 明确说"不做"的东西？
- 每改完一个文件，有没有跑对应的测试？

**产出物**：可运行的代码、数据库初始化脚本、以及对应的自动化测试

**常见错误**：

- 施工过程中悄悄改动了 spec 里的约定——如果你发现 spec 有问题，应该是回去改 spec，而不是在写代码时绕过去
- AI 做完一段后没有及时测试——等到所有代码都写完了才发现某个模块跑不通，返工的代价远高于边写边测

---

## 环节五：review — 找"能跑但会出事"的问题

**目标**：找出功能测试测不出来、但会导致严重后果的隐患。

**操作步骤**：

1. 加载 `/review` 技能，输入本次改动的 diff（或列出改动的文件范围）
2. review 分两遍进行：
   - **第一遍（致命检查）**：SQL 注入、XSS、敏感数据泄露、权限校验缺失——这些问题一旦存在就是事故
   - **第二遍（信息检查）**：边界处理、错误兜底、代码一致性、命名规范

**第一遍必须逐条回答的问题**：

- 所有 SQL 查询是否都用了参数化预编译（`db.prepare()`），没有任何字符串拼接？
- 所有用户可控文本渲染到页面上时，是否经过了转义处理？
- 权限判断是否严格基于服务端数据（从 `req.session` 中读取），没有任何前端可伪造的字段？
- 有没有 API 密钥、密码、Token 硬编码在代码中？
- 越权检查：换个账号登录，能不能访问或操作不属于自己的数据？
- 跨用户信息泄露：A 用户能不能通过修改请求参数看到 B 用户的订单或信息？

**第二遍检查的要点**：

- 每个功能点的失败路径是否有兜底处理？
- 数据库异常、网络超时时，接口返回的是不是可读的错误信息（而不是裸奔的异常栈）？
- 代码结构、命名规范是否与项目已有约定一致？
- 有没有 AI 生成的"死代码"或"重复代码"？

**问题分级**：

- P0：高危漏洞，必须立即修复，阻塞发布
- P1：中度风险，修复后再发布
- P2：低风险，可记录到已知问题清单，不阻塞当前发布
- P3：锦上添花的加固项，可在发布后择机处理

**产出物**：一份 review.md，包含：审查范围、逐条发现（含位置、严重度、说明）、Fix List（按优先级排序）、总体结论（pass/fail）

**常见错误**：

- 只检查了自己写的文件，没检查 AI 新生成的文件
- 只检查了"逻辑对不对"，没检查"会不会被别人利用"——review 和功能测试的区别正在这里
- 对 P3 级别的发现不屑一顾——它们今天不是事故，但未来积累多了就会变成事故

---

## 环节六：qa — 用真实浏览器跑一遍核心流程

**目标**：在真实使用场景下验证应用，而不是相信"单元测试都过了所以没问题"。

**操作步骤**：

1. 启动应用（`node server.js`），确保服务正常运行
2. 加载 `/qa` 技能
3. 用浏览器自动化工具逐个跑一遍核心业务流程
4. 对于权限、越权类测试，追加 curl 直接调用 API 做交叉验证——只验证"前端隐藏了入口"是不够的，必须验证"后端真的拒绝了请求"

**必须覆盖的场景**：

- 正常用户的完整主流程（如注册→登录→浏览→加购→下单）
- 权限边界（顾客能否访问管理功能、未登录能否下单）
- 边界输入（空表单提交、超长文本、负数数量）
- 资源状态变化（售罄商品能否加入购物车、库存不足能否下单）

**交叉验证原则**：每个权限检查点都要做"两遍"——一遍在浏览器里看 UI 是否做了隐藏，一遍用 curl 直接调 API 看后端是否真的返回了 401/403。只验证前者就判定通过是常见的"假安全"陷阱。

**产出物**：一份 qa-report.md，包含：测试环境、测试场景及结果（通过/失败/备注）、发现的问题（含复现步骤）、总体通过判定

**常见错误**：

- 测了正常路径就认为"没问题"——绝大多数的 bug 出现在边界和异常路径上
- 遇到工具本身的抖动（如浏览器点击偶发不响应），不断在同一个操作上重试——应该用 curl 交叉验证，区分"工具问题"和"应用bug"

## 环节七：ship — 规范化收尾

**目标**：把一次开发迭代的成果完整、规范地收尾，让后续接手的人能搞清楚"这一版做了什么、为什么这样做"。

**操作步骤**：

1. 加载 `/ship` 技能
2. 生成/更新版本号（遵循语义化版本规范）
3. 更新 CHANGELOG.md，用简洁的语言记录本次变更
4. 更新 README.md 和其他项目文档（如有结构、启动方式、配置项变化）
5. 确保所有 review/qa 阶段发现的问题已处理或记录
6. 提交代码，commit message 遵循约定格式（如 `feat: add authentication`）

**产出物**：更新的版本号、CHANGELOG.md、README.md、以及已提交的代码

**常见错误**：

- 只提交了代码，没有更新文档——文档和代码不同步，等于埋了颗"以后的人一定踩"的雷
- CHANGELOG 写得太简略——"修复了一些问题"这种描述对后来者毫无帮助

---

## 环节八：retro — 复盘改进

**目标**：回顾这一次完整流程中做得好的地方、遇到的具体摩擦、以及值得改进的环节。

**操作步骤**：

1. 加载 `/retro` 技能
2. 回顾从 office-hours 到 ship 的全程
3. 记录做得好的地方（值得坚持的做法）
4. 记录遇到的具体摩擦（不要写"沟通不畅"这类空话，要写"在 XX 环节因为 YY 原因导致了 ZZ 后果"）
5. 记录未覆盖的测试项（记录下来防止遗忘）
6. 形成改进行动项

**产出物**：一份 retro.md，包含：做得好的、遇到的摩擦、未覆盖的测试项、改进行动项

---

## 附：checklist — 每完成一个环节后自查

- [ ] office-hours：需求本身的合理性确认了
- [ ] spec：失败模式覆盖了、硬边界明确了、数据模型清晰了
- [ ] autoplan：所有两可决策都有人拍板了、结论更新到 spec 了
- [ ] 施工：按 spec 顺序实现了、每个模块测试通过了
- [ ] review：第一遍致命检查跑完了、Fix List 分级了、有总体结论
- [ ] qa：正常路径和异常路径都测了、权限用 curl 交叉验证了
- [ ] ship：版本号更新了、CHANGELOG 写了、README 同步了、代码提交了
- [ ] retro：好的做法记录了、具体摩擦记录了、改进行动项明确了
